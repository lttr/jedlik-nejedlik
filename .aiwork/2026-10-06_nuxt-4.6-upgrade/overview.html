Nuxt 4.6 upgrade: what it is and why

We move to Nuxt 4.6, the release that bridges to Nuxt 5, and use it to clean up the server code. The API becomes type-checked from the server handler to the page. Several workarounds go away. After this, moving to Nuxt 5 should be just a version bump.

1 → 0auth modules (nuxt-auth-utils replaced by Nuxt's own sessions)
~20 → 0files importing from h3
7 → 1copies of the "parse request body" pattern
6 → 0hand-written response types in client calls
3 → alldata fetches that report errors to Sentry
Nuxt 5compatibility mode switched on now
Why now 1 · Type-checked API calls 2 · Server code on nuxt/server 3 · Sessions without nuxt-auth-utils 4 · One input-validation helper 5 · Error reporting by default 6 · Nuxt 5 mode and removed workarounds 7 · Toolchain Order of work What you need to do Risks

Why now

  • Nuxt 4.6 came out on 2026-10-06. Nuxt 3 has been end-of-life since July, so 4.x is the only maintained line, and 4.6 lets you switch on every Nuxt 5 default ahead of time.
  • It adds nuxt/server, a set of server helpers that work the same on Nitro v2 (today) and Nitro v3 (Nuxt 5).
  • It rebuilds typed $fetch: the client knows each route's path, method, body and response, without the "type instantiation is excessively deep" errors.
  • Our blocker was nuxt-auth-utils. It only works with h3 v1, its maintainer said in April it is "not yet ready for Nitro v3", and nothing has moved since. Nobody uses accounts in production yet, so we can simply replace it.

1 · Type-checked API calls

Today the client states every response type itself. A generic on useFetch<T> is an unchecked assertion: if the handler changes what it returns, the page still compiles against the old shape.

Before · MyCourses.vue
import type { OwnedCourse }
  from "#layers/shop/shared/utils/owned-courses"

const { data: courses } =
  await useFetch<OwnedCourse[]>(
    "/api/account/courses",
    { key: "account:courses", default: () => [] },
  )

// typo in the path? wrong method? → runtime 404
await $fetch<{ gwUrl: string }>(
  `/api/checkout/${slug}`, { method: "POST", body })
After
// no import, no generic: the type comes from
// the handler's return type
const { data: courses } = await useApiFetch(
  "/api/account/courses",
  { key: "account:courses", default: () => [] },
)

// path, method and body are type-checked
await $fetch("/api/acount/courses")
//           ^ error: unknown route
await $fetch("/api/checkout/x", { method: "POST",
  body: { consent: "yes" } })
//                ^ error: boolean expected

The handler's return type becomes the single definition of each route's contract. Types the client no longer needs (OwnedCourse, CheckoutView, SettlementView) move from shared/ to the server.

The two settings: experimental.routeTypedFetch and strictRouteTypes. Calls to GoPay switch to an explicitly imported ofetch, so a bare $fetch always means one of our own routes.

2 · Server code on nuxt/server

All handlers, server middleware and server utils import their helpers explicitly from nuxt/server, not from h3 v1 and not through auto-import. The event is the web-standard RequestEvent (event.req is a regular Request).

Before · h3 v1, auto-imported
import type { H3Event } from "h3"

// defineEventHandler, readBody, createError,
// sendNoContent … come from nowhere visible
export default defineEventHandler(async (event) => {
  …
  throw createError({ statusCode: 400 })
  sendNoContent(event)
})

function readCookie(event: H3Event) {
  return event.node.req.headers.cookie
}
After · explicit, portable to Nuxt 5
import { createError, defineEventHandler }
  from "nuxt/server"
import type { RequestEvent } from "nuxt/schema"

export default defineEventHandler(async (event) => {
  …
  throw createError({ status: 400 })
  return new Response(null, { status: 204 })
})

function readCookie(event: RequestEvent) {
  return event.req.headers.get("cookie")
}

The server follows the same rule as the rest of the codebase: every import is visible. The same code runs unchanged on Nuxt 5 / Nitro v3.

Sketch. The exact 204 form and where RequestEvent is imported from get settled during implementation. Watch for the trap: mixing h3's defineEventHandler with nuxt/server helpers in one file gives a NUXT_E8012 500, so each file is converted completely in one go.

3 · Sessions without nuxt-auth-utils

The swap is small because the code already has two places where the session is touched: the server session-store and the client useAccount(). Only those two change. Pages and API handlers still work with Account.

page→ useAccount()→ useUserSession()→ GET /api/_auth/session (internal fetch)
page→ useAccount()→ useState (filled during SSR by the account middleware)
Before · session-store.ts
// getUserSession etc. only reachable via
// Nitro auto-import
export async function readAccountSession(event: H3Event) {
  const { user, secure } = await getUserSession(event)
  return { account: user, secrets: secure }
}

export async function dropAccountSession(event: H3Event) {
  await clearUserSession(event)
  // also strip the cookie from the incoming
  // request, because the module re-reads the
  // session through an internal SSR fetch…
  event.node.req.headers.cookie = cookieHeader
    .split(";").filter(…).join(";")
}
After
import { useSession } from "nuxt/server"

interface StoredSession {
  account?: Account
  secrets?: AccountSecrets
}

const config = { maxAge: THIRTY_DAYS,
  cookie: { httpOnly: true, secure: true,
            sameSite: "lax" } }

export async function readAccountSession(event) {
  const s = await useSession<StoredSession>(event, config)
  return { account: s.data.account,
           secrets: s.data.secrets }
}

export async function dropAccountSession(event) {
  await (await useSession(event, config)).clear()
  // no internal fetch → no hack
}
Before · auth.ts (client)
async logIn(credentials) {
  await $fetch("/api/auth/login",
    { method: "POST", body: credentials })
  await refresh()  // second request to read the session
}
After
async logIn(credentials) {
  account.value = await $fetch("/api/auth/login",
    { method: "POST", body: credentials })
  // login returns the Account, typed
}
  • The cookie is sealed with NUXT_APP_SECRET, the app-wide secret new in 4.6. It replaces NUXT_SESSION_PASSWORD.
  • The Directus tokens stay server-side only, as ADR 0002 requires. The browser only ever gets the Account (e-mail).
  • The 30-day window keeps renewing on use. A unit test covers this.
  • ADR 0002 gets an amendment: the session is sealed by Nuxt itself instead of nuxt-auth-utils. The decision itself doesn't change.

4 · One input-validation helper

The same pattern appears seven times, in auth, shop and mock-GoPay:

Before · billing.post.ts (and six more)
const request = BillingRequestSchema.safeParse(
  await readBody(event).catch(() => undefined))
if (!request.success) {
  throw shopError(400, "invalid_billing",
    shopMessages.billingInvalid)
}
// client body is untyped
After · sketch
import { readValidInput }
  from "#layers/base/server/utils/input"

const billing = await readValidInput(event,
  BillingRequestSchema,
  shopError(400, "invalid_billing",
    shopMessages.billingInvalid))
// built on readValidatedBody → the client body
// is type-checked against BillingRequestSchema

Written once, the same everywhere, and it makes request bodies type-checked on the client. Error replies stay exactly the same, so a malformed body still reveals nothing extra.

The helper's name is illustrative. The first ticket checks whether type inference survives the wrapper. If it doesn't, handlers call readValidatedBody directly and the helper only maps the error.

5 · Error reporting by default

useAsyncData doesn't throw when a handler fails; it quietly returns empty data. That's why watchAsyncDataError() exists, but only 3 call sites remember to call it. Course detail, My Account and checkout don't report anything.

Before
const { data, error } = await useFetch("/api/courses",
  { key, default: () => [] })
watchAsyncDataError(key, error) // if you remember
After · 4.6 add-on
// base layer, once:
export const useApiFetch = createUseFetch({
  addons: [reportErrorsToSentry] })

// everywhere (raw useFetch is banned by lint):
const { data } = await useApiFetch("/api/courses",
  { key, default: () => [] })

6 · Nuxt 5 mode and removed workarounds

future.compatibilityVersion: 5 is switched on as a whole. If a module breaks under one specific Nuxt 5 setting, only that setting is switched off, with a comment saying why and a note in the gap list.

What goes Why it existed Why it can go
Nitro dirsScanOptions filter in nuxt.config To keep our server utils out of auto-import while keeping nuxt-auth-utils' helpers in it Nuxt 5 mode turns Nitro auto-imports off, and nuxt-auth-utils is gone
Exact h3 pin in pnpm-workspace.yaml So our import type { H3Event } from "h3" resolves to v1, not the hoisted v2 rc Our code no longer imports anything from h3
#auth-utils type augmentation and its lint exemption Typing the session for nuxt-auth-utils The session type is an ordinary interface in session-store
runtimeConfig.session nuxt-auth-utils required the whole config there The config lives next to the code that uses it

Nuxt 5 defaults to check by hand, not just by a green build: case-sensitive routing, navigateTo returning early in middleware, PostCSS autoprefixer/cssnano off, Options API compiled out, Capo head sorting, and the error page rendered within the same request.

  4. Server on nuxt/server + the input-validation helper

How it's verified

  • vp run check:all, plus a test that a deliberate wrong path, method and body fail typecheck.
  • Unit tests for session-store (the window renews, tokens never reach the client) and for the input-validation helper.
  • The verify skill: registration → login → My Account → password change → logout → reset, then Catalog → checkout through mock GoPay. At 375px and on desktop.
  • Build, deploy and monitor-deploy, then a smoke test in production.

What you need to do

Before the production deploy: set NUXT_APP_SECRET in Coolify (openssl rand -base64 32, as a string). Production never generates one, so without it no session can be created. Remove NUXT_SESSION_PASSWORD only after the deploy is confirmed healthy, so a rollback still has its secret.

Start on 2026-10-07 or later: Nuxt 4.6.0 is younger than the 24-hour minimumReleaseAge (ADR 0003).

Risks

  • Vite version. @nuxt/vite-builder@4.6.0 asks for vite ^8.3.2, but vite-plus 1.0.0 bundles 8.3.1. If dev, build or HMR break on it, we wait for a vite-plus patch.
  • vitest 5 is a major version that comes with vite-plus. If it grows, it splits into its own task.
  • Modules under Nuxt 5 mode were audited on 2026-10-06 and none is known to break with our config. Sentry is likely to: its middleware wrapper imports from #imports, which doesn't exist with Nitro auto-imports off. The fallback is the single opt-out experimental.nitroAutoImports: true. Two of our own files (the sitemap handler and auth-urls.ts) need explicit imports through the modules' aliases.
